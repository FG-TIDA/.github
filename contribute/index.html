How to contribute to TIDA

TIDA work is organised in work items. Every work item moves through the same lifecycle, and you can contribute at either end of it: improve a work item that exists, or submit a new one.

The lifecycle of a work item

A work item enters the TIDA DataTracker as Submitted. The TIDA DataTracker is the official record and holds the state of every work item; the GitHub repository shows it. Two different questions are answered in turn, by two different bodies: where does it go? is answered by the Focus Group plenary, on a proposal of the incubation committee; is it adopted? is answered by the working group that receives it. A work item that no working group can host yet is not rejected: it waits in the incubation queue until a working group is formed or a charter is amended. Once dispatched to a working group, the work item stays there: it is adopted or rejected by that group.

Work Item States:

Submitted
Submitted to the TIDA DataTracker before the contribution deadline, with a declared target: a working group, or "NWI for Incubation". It stays Submitted until the plenary decides where it goes and, if allocated to a working group, until that group decides on adoption.
Incubated
In the incubation queue: valid for TIDA, but NWI for Incubation can host it yet. The incubation committee reviews the queue before each meeting. It leaves the queue when a working group is formed or a charter is amended to host it. A work item that has stalled in the queue for more than six months, with no contribution and no activity, is rejected on the committee's report, unless the plenary decides otherwise.
Rejected
Not adopted by the working group it was allocated to (the group states the reason), or stalled in the incubation queue for more than six months. Final: a new contribution is needed.
Under review
Adopted by its working group. The repository exists in the working group's organisation; the group writes and reviews the work item, and every change arrives as a pull request.
Published
The working group has approved the work item and the editors have published it. The work item is final.

Who decides what, and when

Contribution deadline By default 10 days before the meeting, unless agreed otherwise (the time schedule adopted by the Focus Group under A.7 clause 3.3). Contributions submitted after the deadline are taken at the next meeting.
Incubation committee A small group designated by the Focus Group for each meeting: participants who know the procedure well, whether or not they hold a role in the Focus Group; working group chairs may join. Between the deadline and the meeting it reads every contribution and proposes a dispatch table: declared target, proposed target, one reason when the two differ. It keeps the incubation queue and reports its status before each meeting (what is in it, what clusters are forming, what could be reallocated, what has stalled for more than six months and is proposed for rejection), and convenes ad hoc groups to draft or amend charters. It does not judge content and it decides nothing.
Plenary, first day Takes the dispatch table and the queue report in one of the first sessions (one hour at the first meeting, less afterwards). Decides immediately what can be decided: dispatch to existing working groups, reallocation out of the queue, creation of an ad hoc group to draft or amend a charter during the meeting.
Working groups, during the meeting Decide adoption of the work items allocated to them. A work item not adopted is rejected; the group states the reason and the contributor may submit a new contribution.
Plenary, last day Decides what was prepared during the meeting: new working groups, amended charters, reallocations from the queue. A charter that is not ready is agreed provisionally on the mailing list after the meeting and confirmed at the next plenary.
Reasons in the dispatch table T1 NWI for Incubation covers it yet · T2 more than one working group could host it · T3 another working group fits better: working groups overlap by nature and a contributor can pick the wrong one (for example a use case sent to a horizontal group) · T4 outside the terms of reference or excluded under A.7: not dispatched, referred to the FG Co-Chairs and the SG17 Chair.

This process is inspired by the incubation mechanism of FG-TIDA's parent group, ITU-T Study Group 17, published as the ITU-T Technical Paper TP.inno, Description of the incubation mechanism and ways to improve it (03/2024) . The mechanism has been modified and adapted to suit the agile nature of this Focus Group.

How to contribute

Contribute to an existing work item

The work item lives in its working group's GitHub organisation. You propose changes; the working group decides. Please, before proceeding, make sure you have GitHub account created.

Applies while the work item is Under review
  1. 1
    GitHub

    Find the work item

    Open your working group's GitHub page, for example github.com/fg-tida-wg2. Its table of deliverables links each work item's published site, PDF and repository (wg<n>-<acronym>-<name>). The chairs and mailing list are listed there too.

  2. 2

    What do you want to do?

    Change the text

    Open a pull request

    1. In the browser: open a file under src/doc/, click the pencil, choose Propose changes.
    2. Or with Git: branch, edit, push, then open a PR against main.

    You cannot push to main directly (it is protected).

    Report a problem or ask a question

    Open an issue

    A clear title and a short description of what is wrong and where is enough to start.

    Discuss direction or larger questions

    Write to the mailing list

    Before drafting anything substantial, discuss your idea with the working group through the mailing list linked on its WG page.

    To subscribe: Create a free ITU user account if you do not already have one, then sign in and open the FG-TIDA mailing-list subscription page . Follow the on-screen instructions to subscribe. Once subscribed, use the mailing-list address linked on your WG page to share your question or proposal with the group.

  3. 3
    GitHub

    The working group reviews

    Every pull request is reviewed by the working group before it is merged, so each change keeps a review and decision history.

  4. 4
    GitHub TIDA DataTracker

    Merged into main

    Each push to main rebuilds the HTML site and PDF and publishes them to GitHub Pages. The same build is sent to the TIDA DataTracker, which always holds the latest working copy of the work item.

  5. 5
    GitHub TIDA DataTracker

    Release: tag vX.Y becomes revision X.Y

    When the editors tag a release, HTML site, the PDF, source archive and a manifest go to the TIDA DataTracker, which records revision X.Y of the work item.

    Merges between releases update the working copy only. They do not create a revision.

Submit a new work item

Prepare a complete source contribution from the common template, then submit it through GitHub or a ZIP upload. A Word fallback is available when technical assistance is needed. The TIDA DataTracker is the official record.

Takes a work item from Submitted to Under review, directly or through the Incubated queue
  1. 1
    GitHub

    Prepare your contribution using the common template

    Start with the FG-TIDA specification template . Include a title, abstract, authors, proposed scope and technical content. Keep the RST chapters, images, diagrams and references together, using relative paths so the contribution can be read and built independently.

    Choose one of two source submission routes

    Recommended for GitHub users

    Option 1 · GitHub repository

    1. You need your own GitHub account for this method. If you do not have one, create a GitHub account , then sign in.
    2. Open the specification template and select Use this template → Create a new repository. Set Owner to your own GitHub username, choose a repository name and select Public. Create the repository in your personal account; this is your draft workspace.
    3. In your new repository, edit the .rst files: these are the text files containing your chapters. Replace the template examples with your contribution. Add every image, diagram and reference file that your text uses. Keep editable diagram sources when available.
    4. Follow the build instructions in the template's CONTRIBUTING.md (sections 2 and 3) to generate the reading version. Review the HTML or PDF and resolve missing images and build errors before submitting.
    5. Save your completed changes as a commit in your repository. A commit records an exact version of your files. Open that commit in GitHub and copy its full SHA (the long identifier), not just the branch name. Keep it for the submission form below.

    You do not need permission to create repositories in the target WG organisation. The official WG repository is established after adoption.

    No GitHub account required

    Option 2 · Direct ZIP upload

    1. Open the same template repository and choose Code → Download ZIP.
    2. Unzip the downloaded file on your computer. Open the .rst files in a text editor and replace the template examples with your contribution. Keep the folders in their original arrangement and add every image, diagram and reference file used by your text.
    3. Keep the template's configuration and requirements files: these describe how to generate the document. Do not include passwords, access tokens, installed software folders or generated build output.
    4. Follow the build instructions in CONTRIBUTING.md (sections 2 and 3) to check your document if possible. Then compress the completed template folder into one .zip file. Upload this edited ZIP, not the original template download. Note the path to the main RST file, normally src/doc/index.rst; this is the entry document.

    You work on your computer and upload the ZIP to the DataTracker; you do not need to create a GitHub account or repository. Include the image and diagram files themselves, not just links to them. Keep their paths relative to the document, for example images/architecture.png, rather than a path on your computer.

    Exceptional fallback: Word (.docx) — discouraged

    Use this exceptional route only if you cannot prepare an RST contribution, even using the ZIP method. Write your contribution in Word and save it as .docx. You do not need a GitHub account or any knowledge of RST. You will upload the Word file directly to the DataTracker and request conversion assistance.

    Use clear heading levels and include the title, abstract, authors, scope, references, captions and embedded figures. Supply original images and editable diagrams as supporting files where available, and briefly explain that you need help converting the document.

    Word is an accessibility fallback, not the normal standards source format. Editors coordinate conversion to the common RST template, and the contributor checks that the converted text, figures and references are faithful. The original submission remains archived; the verified RST becomes the maintained source.

  2. 2
    TIDA DataTracker Submitted

    Submit the complete contribution in the TIDA DataTracker

    All three routes require a TIDA DataTracker account. If you do not have one, register and complete the account confirmation, then sign in. A GitHub account does not replace this account. Submit before the contribution deadline shown for the meeting (the proposed default is 10 days before the meeting). Under Documents → Submit NWI(New Work Item) , enter the title, abstract, authors and target: a working group or NWI for Incubation. Choose the submission method that matches what you prepared above.

    Submit from GitHub

    Select GitHub repository and enter the details of your completed repository in your own account, not the template repository:

    1. Repository URL: for example, https://github.com/YOUR-USERNAME/YOUR-REPOSITORY.
    2. Source folder: the folder containing your documentation, normally src/doc.
    3. Entry document: the main RST file, given as a path from the repository root, normally src/doc/index.rst.
    4. Commit SHA: paste the full identifier of the completed version you want the WG to review.

    Use the actual paths in your repository if they differ from these examples. Keep every referenced asset inside the source folder. A link to main is not an exact version. You do not need to upload a ZIP as well.

    The DataTracker validates the selected source and preserves a snapshot of that commit's contribution files and assets, together with their provenance. Later changes in your repository do not alter this submission; submit a new revision deliberately.

    Submit a ZIP package

    Select RST source package (.zip), choose the completed ZIP from your computer and upload it. Enter the path to the main RST file inside the ZIP, including any enclosing folder, for example my-contribution/src/doc/index.rst. No GitHub account, repository URL or commit SHA is required.

    The DataTracker checks the package structure and referenced assets, preserves the original ZIP and records the source snapshot for this revision.

    For the exceptional Word route, select Word (.docx) — request conversion assistance, upload the document and any supporting assets, and explain the assistance needed. The submission is marked as needing source conversion; using Word does not bypass review or imply adoption.

    For RST submissions, validation and the documentation build provide a reading preview. Resolve reported errors before confirming. Preview the title, authors, target and files: the confirmed contribution is public. The DataTracker then assigns a contribution identifier and archives the submitted revision with status Submitted. A repository link alone does not enable synchronisation.

    Where do you think it belongs?

    It fits an existing working group

    Declare that working group

    Pick the group in the submission form. Today: WG0 Use Cases and Terminology, WG1 Continuous and Dynamic Remote Attestation for Agentic AI (CDRA), WG2 Identity, Behaviour and Enforcement for AI Agents (IBEA). Groups overlap by nature: if you hesitate, say so in the abstract.

    NWI for Incubation covers it yet

    Declare "NWI for Incubation"

    Pick NWI for Incubation in the form. Say in the abstract whether you see it as a new group or as an extension of an existing charter.

    The work item is Submitted straight away.

  3. 3
    TIDA DataTracker Mailing list Submitted

    The plenary decides where it goes

    Between the deadline and the meeting, the incubation committee reads every contribution and publishes a dispatch table. In one of the first sessions of the meeting, the plenary decides. The work item stays Submitted until then.

    A working group can host it

    Allocated to that working group

    The working group, which may differ from the one you declared, decides adoption during the meeting. The work item stays Submitted until then.

    Under review if it adopts. Rejected if it does not: the group states the reason, and you may come back with a new contribution.

    NWI for Incubation can host it yet

    Incubated

    Incubated: the work item waits in the incubation queue. The incubation committee reviews the queue before each meeting; when enough work items cluster, an ad hoc group drafts a new charter from wg-charter-template (wg<n>-<acronym>-charter) or amends an existing one, and the plenary decides. The work item is then allocated to that group and goes Under review in it. A work item that stalls in the queue for more than six months, with no contribution and no activity, is Rejected: the queue is a waiting room, not a shelf.

    A contribution outside the FG-TIDA terms of reference, or excluded under A.7 because the subject is already handled elsewhere, is not dispatched: the FG Co-Chairs and the SG17 Chair resolve it with the contributor before the meeting, and the work item is removed from the DataTracker or resubmitted within scope.

  4. 4
    GitHub TIDA DataTracker Under review

    Establish the official repository in the adopting WG organisation

    On adoption, editors establish the official repository inside the adopting working group's GitHub organisation, using the common template and the name wg<n>-<acronym>-<name>. For example, a WG1 work item belongs in fg-tida-wg1. The declared target may have changed during allocation; the adopting WG determines ownership.

    For a GitHub submission, WG editors import the reviewed source snapshot and all its assets from the recorded commit in your personal repository. For a ZIP submission, WG editors import the reviewed package; you do not have to create the official repository yourself. For a Word submission, editors arrange conversion to RST and contributor verification before establishing the maintained source. The repository must contain the actual contribution, not just an empty template.

    Editors: import a GitHub submission with its history

    Use the commit recorded in the TIDA DataTracker, never main. Create an empty repository named wg<n>-<acronym>-<name> in the working group organisation (no README, no template files), then run:

    git clone https://github.com/PROPOSER/REPO.git wg-import
    cd wg-import
    git checkout -b main FULL-SHA
    git remote add wg https://github.com/fg-tida-wg<n>/wg<n>-<acronym>-<name>.git
    git push wg main

    This keeps the proposer's history and authorship up to the reviewed commit and leaves out any later changes. Then set Settings → Pages → Source: GitHub Actions, protect main, assign maintainers and link the repository to the same DataTracker record. For a ZIP submission, create the repository from the template, unzip the package into it and commit with the proposer as author.

    Editors assign maintainers, check the build and configure the approved publishing integration. The DataTracker links the official repository to the same contribution record, retaining the original submission, its provenance and the adoption decision.

    Subsequent changes use pull requests in the official WG repository. Successful main-branch builds update the working copy; formal releases archive numbered revisions with their source and assets. Builds and repository creation do not themselves approve or publish the work item.

  5. ●
    It is now an existing work item. From here, everyone contributes through the path for an existing work item.
